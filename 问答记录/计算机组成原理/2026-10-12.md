## 20:27　`CO-补漏-2024`　截断与扩展、数组地址与负数机器数、Cache 与虚存、中断两种优先级

**用户要求**：2024 整卷计组错 12、18，43 丢约 3 分（shamt 取自 IR[24:20]），44 丢约 6 分（a[i] 地址、a[i] 机器数、sum 机器数）；14、15、16、21、22 拿不准但做对。补这四块，按“漏洞→补法→迁移检验”，不重做原题。

### 一、截断与符号扩展（关联 2024-12、2024-43）

**漏洞**：截断后只想到“溢出”，没算出新值；扩展时零扩展、符号扩展分不清什么时候用、会不会改值；读指令时没对着格式表看字段位置。

**补法**
1. 截断（长 → 短）：只留低 n 位，按新类型重新解释。值的算法：新最高位是 0，值就是低 n 位；是 1（有符号），值 = 低 n 位的无符号值 − 2ⁿ。原值在新类型范围内时，截断不改值。
2. 扩展（短 → 长）：看**源类型**。有符号数做符号扩展（高位全补符号位），无符号数做零扩展（高位全补 0）。扩展永远不改值，改变的只是机器数长度。
3. 所以 short → int 的两步链是“先截断可能改值，再扩展保持这个新值”。
4. 指令里的立即数同理：要参与有符号运算的偏移量、立即数做符号扩展；移位量是无符号的位数，只看格式表规定的那几位（32 位机器是 5 位），先在格式表上把字段的位段标出来，再说扩展。

**检验**：(a) unsigned short us = 0xFF9C; int x = us; short s = us; int y = s; 求 x、y 的值和 32 位机器数（十六进制）。(b) int i = −70000; short t = i; 求 t 的值。待用户作答。

### 二、数组元素地址与负数补码机器数（关联 2024-44）

**漏洞**：地址公式没先写出来就代数；负数写成 32 位补码时没有稳定算法。

**补法**
1. 一维：&a[i] = 首地址 + i × 元素字节数（按字节编址）。int 占 4B 时 i × 4 就是 i 左移 2 位，先把 i×4 换成十六进制再加。
2. 二维按行优先：&a[i][j] = 首地址 + (i × 列数 + j) × 元素字节数。
3. 负数 n 位补码机器数 = 2ⁿ − |x|。十六进制快算：先写 |x| 的十六进制并补满位数，每一位用 F 减（逐位取反），最后加 1。例：−20，20 = 0000 0014H → FFFF FFEBH → +1 = FFFF FFECH。
4. 自查：机器数 + |x| 应该正好进位成 1 0000 0000H；最高位必须是 F 系列（符号位 1）。

**检验**：short b[50][20] 按行存放，首地址 0040 2000H，short 占 2B。(a) &b[3][7] 是多少？(b) 若 b[3][7] = −1000，写出它的 16 位机器数；把它赋给 int 变量后，32 位机器数是多少？待用户作答。

### 三、Cache 与虚拟存储器对比（关联 2024-16、2024-18）

**漏洞**：两个层次的映射方式、替换由谁做、写策略混在一起；访存时 MMU 和 Cache 的先后不清。

**补法**

| 对比项 | Cache—主存 | 主存—辅存（虚存） |
|---|---|---|
| 目的 | 解决速度 | 解决容量 |
| 交换单位 | 块（行），几十字节 | 页，KB 级 |
| 实现 | 全部硬件 | 硬件（MMU、TLB）+ 操作系统 |
| 映射方式 | 直接、全相联、组相联 | 全相联（任一页可放任一页框，靠页表记录） |
| 缺失处理 | 硬件调块，等几十个周期，不切换进程 | 缺页异常，OS 调页，代价极大，会切换进程 |
| 替换算法 | 硬件实现（LRU、FIFO、随机） | OS 软件实现（LRU 近似、CLOCK 等） |
| 写策略 | 写直达或写回 | 只能写回（写磁盘太慢） |
| 透明性 | 对所有程序员透明 | 对应用程序员透明 |

共同点：都靠局部性原理，都有命中/缺失，都要“标记”（Cache 的 tag、页表的页号对应关系）。
访存顺序：虚拟地址 → 查 TLB → 未命中查页表（缺页则异常）→ 得物理地址 → 查 Cache → 未命中访主存。越权、缺页、TLB 缺失都在地址转换（MMU）阶段发现，Cache 缺失在得到物理地址之后。

**检验**：(a) 为什么虚存只能用写回，不用写直达？(b) 为什么虚存用全相联，Cache 却常用组相联？(c) 一次访存中，“TLB 命中、Cache 缺失、缺页”三者能不能同时出现？为什么？待用户作答。

### 四、中断响应优先级与处理优先级（关联 2024-21）

**漏洞**：把“谁先被响应”和“谁能打断谁”当成一回事，以为屏蔽字能改响应顺序。

**补法**
1. 响应优先级：多个中断请求**同时**到来时，CPU 先响应谁。由硬件判优电路（排队器、链式查询等）固定决定，软件改不了。
2. 处理优先级：正在执行某个中断服务程序时，新来的请求能不能**打断**它。由中断屏蔽字决定，软件可以改。
3. 屏蔽字读法：每个中断服务程序有自己的屏蔽字，某位为 1 表示屏蔽那个源。一般屏蔽自己和处理优先级比自己低的源，不屏蔽比自己高的。
4. 被屏蔽的请求不会丢，只是挂着，等屏蔽解除后再被响应。
5. 和 2010-21 连起来：屏蔽字在服务程序里“保存现场和屏蔽字”那一步设置，只在多重中断里起作用。

**检验**：4 个中断源 L0～L3，响应优先级 L0 > L1 > L2 > L3。(a) 要让处理优先级变为 L1 > L3 > L0 > L2，写出每个服务程序的屏蔽字（按 L0 L1 L2 L3 顺序，1 表示屏蔽）。(b) L0 和 L2 同时请求，先响应谁？L0 服务程序执行中 L3 请求，会不会打断 L0？待用户作答。
